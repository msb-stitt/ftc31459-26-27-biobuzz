# 113 lesson: work out where the robot is from the drive wheels

:::{figure} ../_figures/fig-l113-shadow-still.png
:name: fig-l113-shadow-still
:figclass: file-named

fig-l113-shadow-still.png
:::

Your own localizer runs beside the robot's own, and both are published so they can be graphed
against each other. Yours counts how far the four drive wheels roll. A tape measure checks it.

::::{only} mentor
**Before you start.**

- L110 is done, so the follower holds a real drivetrain.
- AdvantageScope is installed on the same laptop, and a gamepad is plugged into the laptop.
- The robot on blocks, as in L050, the Driver Station, a tape measure, and about 3 m of clear floor
  for the last step.

The simulator turns each wheel's encoder by how far the wheel rolls, at `Constants.ticksPerInch`,
and turns the IMU with the robot. It has no slip, so a finished localizer follows the simulator's
own localizer there more closely than it will on the robot. The tests check the arithmetic step by
step. The Pinpoint is not needed: L115 mounts it, and L132 compares the two.
::::

### L113S040: add up how far the wheels rolled

`update` runs once a loop. Each time, it can only see how far each wheel has rolled in total, so it
remembers last loop's numbers and takes them away.

The first loop has nothing to take away from, so it only remembers.

**Change.** Press Ctrl+C in the Terminal to stop the simulator. Open `L113EncoderLocalizer`. In
`update`, find the comment that names this step. Under it, type:

```{code-block} java
:caption: mytry/L113EncoderLocalizer.java
:emphasize-lines: 4-19

        // When on L113S040, see
        // https://coding.stitt.cc/ftc-lessons-java/guide/tasks/l113.html#l113s040
        // for what to do here.
        if (lastWheels_in == null) {
            lastWheels_in = wheels_in.clone();
            lastRawHeading_rad = rawHeading_rad;
            return;
        }

        double[] delta_in = new double[wheels_in.length];
        for (int i = 0; i < wheels_in.length; i++) {
            delta_in[i] = wheels_in[i] - lastWheels_in[i]; // Your math operation here
        }

        double forward_in = (delta_in[FL] + delta_in[FR] + delta_in[BL] + delta_in[BR]) / 4.0;
        double strafe_in = (-delta_in[FL] + delta_in[FR] + delta_in[BL] - delta_in[BR]) / 4.0;

        x_in += forward_in;
        y_in += strafe_in;
```

Android Studio types the `}` for you when you press Enter after the `{`. Type the rest below it.

`null` means "nothing yet". `.clone()` makes a copy, so next loop's numbers do not change it.
`return` leaves `update` early, until next loop. The end of a name says its unit: `_in` is inches,
and `_rad` is radians.

The `for` line runs the line inside it once for each wheel, with `i` at 0, 1, 2 and then 3, so
`delta_in` holds how far each wheel rolled since last loop. `FL`, `FR`, `BL` and `BR` are 0, 1, 2
and 3, the front left, front right, back left and back right wheels' places in it.

The two long lines are L090's table read backwards. There, three numbers made four wheel speeds.
Here, four wheel moves make `forward_in` and `strafe_in` again.

**Check.**

- In the Terminal, run this. It prints `8 tests completed, 2 failed`, then `BUILD FAILED` and more
  red lines. That is what failing tests look like here, and two are meant to fail now.

  ```
  ./gradlew :TeamCode:testDebugUnitTest --tests '*L113EncoderLocalizerTest*'
  ```

The two that fail are
`appliesTheHeadingSoSidewaysIsRelativeToTheRobot` and
`setPoseMovesTheEstimateWithoutMovingTheRobot`. Both are about which way the robot faces. That is
the next step.

### L113S050: turn the step to face the way the robot faces

:::{figure} ../_figures/fig-odometry-step.png
:name: fig-odometry-step
:figclass: file-named

fig-odometry-step.png
:::

`forward_in` is forward for the robot, not for the field. The robot starts facing along the
field's y, so its forward is the field's y. L113S040 added it to x.

**Change.** Delete the two lines `x_in += forward_in;` and `y_in += strafe_in;`. Find the comment
that names this step. Under it, type:

```{code-block} java
:caption: mytry/L113EncoderLocalizer.java
:emphasize-lines: 4-8

        // When on L113S050, see
        // https://coding.stitt.cc/ftc-lessons-java/guide/tasks/l113.html#l113s050
        // for what to do here.
        double heading_rad = rawHeading_rad + headingOffset_rad;
        double sinHeading = Math.sin(heading_rad);
        double cosHeading = Math.cos(heading_rad);
        x_in += forward_in * cosHeading - strafe_in * sinHeading;
        y_in += forward_in * sinHeading + strafe_in * cosHeading;
```

`Math.cos` and `Math.sin` share the step out between x and y. Facing along x, `cos` is 1.0 and `sin`
is 0.0, so forward all goes on x. Facing along y, `cos` is 0.0 and `sin` is 1.0, so forward all goes
on y. In between, each gets a part.

`heading_rad` counts in **radians**, not degrees. One whole turn is about 6.28 radians. `Math.cos`
and `Math.sin` use radians.

**Check.**

- Run the same test command again. It ends with `BUILD SUCCESSFUL`.

:::{figure} ../_figures/fig-l113-encoders-follow.png
:name: fig-l113-encoders-follow
:figclass: file-named

fig-l113-encoders-follow.png

**Simulator.** Run the command from L113S030 again, and connect AdvantageScope.

**Check.**

- Push the left stick forward. This time `driveWheelEncoders/y_in` climbs with `pinPoint/y_in`, and
  the two stay within a tenth of an inch.
- Let go, then push the left stick to the left. `pinPoint/x_in` goes down, and

The simulator turns each wheel's encoder by how far it rolls, so your localizer has something to
count.

:::{figure} ../_figures/fig-l113-wheel-vectors.png
:name: fig-l113-wheel-vectors
:figclass: file-named

fig-l113-wheel-vectors.png
:::

Why does sliding read too far? A mecanum wheel pushes the robot at an angle. On paper the angle is
45 degrees from forward, so its forward part and its sideways part are the same size. In this
simulator the push is 40 degrees from forward, so each push has a longer forward part than
sideways part.

Driving forward, the four forward parts add up, and the sideways parts cancel. Sliding left, the
sideways parts add up, and the forward parts cancel. The sideways sum is shorter, so the same
wheel turns slide the robot less far than they drive it forward. Your localizer takes the push to
be at 45 degrees, so it counts more slide than the robot made. L132 measures the angle.

### L113S060: work out ticks per inch from the parts

Your localizer turns ticks into inches with `ticksPerInch`, a number in the robot's own file. It is
45.0 until you change it. Before you use a number, work it out.

The motor's page on goBILDA's site gives its **encoder resolution**: how many ticks it counts for
one turn of its output shaft. The wheel's page gives its diameter. On the Strafer chassis, these
are the pages:

- The [312 RPM motor][motor] reads "537.7 PPR at the Output Shaft". PPR means ticks per turn.
- The [GripForce wheel][wheel] reads "Ø104mm", a diameter of 104 mm.

[motor]:
  https://www.gobilda.com/5203-series-yellow-jacket-planetary-gear-motor-19-2-1-ratio-24mm-length-8mm-rex-shaft-312-rpm-3-3-5v-encoder/
[wheel]: https://www.gobilda.com/gripforce-mecanum-wheel-set-o104mm-40a-durometer-rollers/

On the Strafer, two gears with 24 teeth each join the shaft to the wheel, so one turn of the shaft
is one turn of the wheel.

One turn rolls the wheel once around its edge, which is pi times its diameter. 104 mm is
104 ÷ 25.4 = 4.09 in, so one turn rolls 3.14 × 4.09 = 12.86 in. Then 537.7 ticks ÷ 12.86 in is
41.8 ticks per inch.

**Change.** Open the file of the robot `thisRobot` names, in the `pedro` folder, such as
`Bot37523`. Change the line `static double ticksPerInch = 45.0;` to work it out from the robot's
parts. For the Strafer, it reads:

```{code-block} java
:class: example

    static double ticksPerInch = Calibration.ticksPerInchFromTheParts(537.7, 104);
```

`Calibration` turns red. Click it, and press Option+Enter on a Mac, Alt+Enter on Windows, to
import it, as in L113S030.

**Check.**

- Run this in the Terminal. It ends with `BUILD SUCCESSFUL`.

  ```
  ./gradlew :TeamCode:testDebugUnitTest --tests '*CalibrationTest*'
  ```

`ticksPerInchFromGoBildasParts` checks the same sum: 537.7 ticks and 104 mm give 41.8.

### L113S070: work out the turn radius from where the wheels sit

`turnRadiusInches` says how far a wheel's rim rolls each time the robot turns one radian. Your
localizer reads its heading from the IMU, so it does not need this number. L131 measures it, and
L190 uses it.

:::{figure} ../_figures/fig-l113-rectangle.png
:name: fig-l113-rectangle
:figclass: file-named

fig-l113-rectangle.png
:::

**Measure.** Look at the robot from above. The four wheel centres make a rectangle. Measure its
length, front to back, and its width, side to side, from the middle of one wheel to the middle of
the next. Half the length is **A**. Half the width is **B**. The rectangle's two diagonals cross at
the middle of the robot, and that is where it turns.

:::{figure} ../_figures/fig-l113-circle.png
:name: fig-l113-circle
:figclass: file-named

fig-l113-circle.png
:::

As the robot turns, each wheel centre goes around a circle through all four. Its radius is half a
diagonal. By Pythagoras, that is √(A² + B²).

:::{figure} ../_figures/fig-l113-x-drive.png
:name: fig-l113-x-drive
:figclass: file-named

fig-l113-x-drive.png
:::

On an **X-drive**, each omni wheel is turned to sit along that circle. It rolls the whole way
round, so its turn radius is √(A² + B²).

:::{figure} ../_figures/fig-l113-mecanum-turn.png
:name: fig-l113-mecanum-turn
:figclass: file-named

fig-l113-mecanum-turn.png
:::

A mecanum wheel points straight ahead, not along the circle. Its centre's move splits into two
parts. The forward part is B for each radian, and the wheel rolls it as when driving forward. The
sideways part is A for each radian, and the wheel rolls it as when sliding, as in L090. So the rim
rolls A + B. With A = 6.5 in and B = 7 in, the turn radius is 13.5 in, not 9.55 in.

**Change.** In the same file, change the line `static double turnRadiusInches = 8.0;` to use
the robot's own A and B. With A = 6.5 in and B = 7 in, it reads:

```{code-block} java
:class: example

    static double turnRadiusInches = Calibration.turnRadiusFromTheWheels(6.5, 7.0);
```

**Check.**

- Run the same test command again. It ends with `BUILD SUCCESSFUL`.

`theTurnRadiusIsHalfTheLengthPlusHalfTheWidth` checks A + B, and fails if the sum is the diagonal.

::::{only} mentor
**No gamepad.** `--args="mytry.L113LocalizerOpMode --left_stick_y=-0.5"` drives forward
for the picture at the top, and for L113S050's.

**If it didn't**, and `driveWheelEncoders` is missing from the `Localizer` folder in L113S030, the
three lines are not in `shadowLocalizers()`.
`LessonsTest.l113_theEncoderLocalizerRunsAlongsideAndIsLogged` fails with
`the shadow localizer is logged:` and the list of names that were published.

**If it didn't**, and `countsStrafingLeft` fails with `left is +y when facing +x`, a sign in the
`strafe_in` line is wrong. With the sign in front of `delta_in[FR]` flipped, it reads
`expected:<12.0> but was:<6.0>`, and three other tests fail with it.

**If it didn't**, and all 8 tests fail with
`Cannot load from double array because "this.lastWheels_in" is null`, the first-loop `if` is
missing.

**What you just did.** That is **dead reckoning**: believe the wheels, and add up every step. It
has no other source, so a wheel that spins without carrying the robot moves the estimate. The test
`aWheelThatSlipsIsSimplyBelieved` shows it on a laptop: one wheel rolling 24 in on its own moves
the estimate 6 in. L115 mounts the Pinpoint, whose pods only measure and never push, so they slip
less. L132 runs yours beside it.

The heading here is the one at the end of each step. While driving and turning at once, the middle
of the step would be closer. Taking the end needs no subtraction of two
headings, so a turn through the back of the circle needs no care.

The localizer reports a speed of zero. Only `x_in`, `y_in` and `heading_deg` are published for a
shadow, so nothing reads its speed.

**If it didn't**, and `theTurnRadiusIsHalfTheLengthPlusHalfTheWidth` fails, the turn radius is
the diagonal. With `Math.hypot(halfLength_in, halfWidth_in)` planted in `Calibration`, it fails with
`A + B, not the hypotenuse, 9.55 expected:<13.5> but was:<9.5524865872714>`.

**The robot's numbers.** The Strafer's motor and wheel are from goBILDA's pages, read 2026-10-31.
A, B and the robot's other parts are its own, and are not checked here.
