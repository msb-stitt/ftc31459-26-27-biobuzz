# 111 what's happening: the classes your OpMode builds on

When the computer runs your program, it reads one line of code at a time. It moves words and
numbers around in its memory. It is like moving sticky notes around on your desk.

In [L110](l110.md) you wrote two classes, `L110FollowerOpMode` and `L110FollowerDriveTrain`. Each
one builds on classes you did not write. This page draws them as UML, as [E067](e067.md) and
[L093](l093.md) did, a little at a time.

## who wrote what

Your code is given a lot that you did not write. The diagrams put each class in a grey box that
says who wrote it:

- **FTC Platform** is the FTC software that runs on the robot. It runs your OpMode.
- **Pedro Pathing** is the path follower's code.
- **Our base classes** are in `base/`. Our team wrote them for these lessons.

Your classes are outside the boxes.

## is-a

:::{admonition} fig-e111-is-a
:class: pencil
Stand-in for `fig-e111-is-a`, made by `book/tools/draw.py`.
:::

An arrow with a hollow triangle means **is-a**: the class is a "kind of" the class the triangle
points at, the class it builds on.
It is the word `extends`. `L110FollowerOpMode extends CorbelsTeleOp`, so an `L110FollowerOpMode`
is a `CorbelsTeleOp`, which is a `CorbelsOpMode`, which is an `OpMode`.

A class gets everything the classes above it have. That is why `gamepad1` and `hardware` work in
your OpMode, though you never made them. `gamepad1` comes from `OpMode`, and `hardware` from
`CorbelsOpMode`. Each lesson's OpMode since L020 has started with `extends CorbelsTeleOp`.

- `«interface»` on `Drivetrain` marks a list of methods with no code in them. A dashed line with a
  hollow triangle means is-a too, for an interface. It is the word `implements`.
  `CorbelsDriveTrain implements Drivetrain`, so it has to write each of those methods.
- `«abstract»` on `CorbelsDriveTrain` marks a class that leaves a method for the class below it.
  It leaves `mixArcadeToWheelSpeeds`, and you wrote it in L110S030.

`@Override` sits above a method that a class above already names. `OpMode` names `init()` and
`loop()` with no code, so each OpMode has to write them. `CorbelsOpMode` already has a `start()`
and a `stop()`, and yours replace them.

Your `init()` calls `initBefore()` and `initAfter()`. Those are `final` in `CorbelsOpMode`: a class
below can call them, but it cannot replace them.

## has-a

:::{admonition} fig-e111-has-a
:class: pencil
Stand-in for `fig-e111-has-a`, made by `book/tools/draw.py`.
:::

An arrow with a diamond means has-a, as in E067. On an arrow from your OpMode, the word is the
name of the field.

- Your OpMode holds (has-a) `hardware` and `follower`. `CorbelsOpMode` declares them, and your
  OpMode gets them.
- You typed `drivetrain` and `stickShaper`.
- The follower holds your drivetrain too, from `initAfter(drivetrain)`. It holds it as a
  `Drivetrain`. It does not know your class, only that it is a "kind of" (is-a) `Drivetrain`. So it
  can drive any drivetrain that is.
- `RobotHardware` holds the robot's motors. In the simulator, the same `hardware` holds simulated
  motors, so your code runs on both without a change.

`Platform` is not a class in the code. It stands for the FTC code that runs your OpMode.

## what the platform calls

:::{admonition} fig-e111-run
:class: pencil
Stand-in for `fig-e111-run`, made by `book/tools/draw.py`.
:::

This sequence diagram starts with a stick figure: the driver. When the driver presses INIT, the
platform calls `init()` once. Then it calls `init_loop()` over and over, until PLAY. A box marked
`loop` holds calls that happen again and again.

Your code never calls `init()` or `loop()`. The platform does, when the Driver Station's buttons
are pressed. Each note names the diagram that shows what the call does.

### INIT

:::{admonition} fig-e111-init
:class: pencil
Stand-in for `fig-e111-init`, made by `book/tools/draw.py`.
:::

- `initBefore()` finds the robot's motors, and sets `hardware`.
- `new` makes your drivetrain, handed `hardware`.
- `initAfter(drivetrain)` makes the follower, holding your drivetrain.
- Until PLAY, each `init_loop()` asks the follower where the robot is. Your OpMode has no
  `init_loop()` of its own; it gets the one in `CorbelsOpMode`.

### PLAY

:::{admonition} fig-e111-play
:class: pencil
Stand-in for `fig-e111-play`, made by `book/tools/draw.py`.
:::

- `start()` hands `driveFromTheSticks` to the scheduler, once.
- Each `loop()` ends with `loopAfter()`. That runs the scheduler, which calls your
  `driveFromTheSticks()`. Each stick goes through `shaped()`, and `sticks(...)` saves the wheel
  speeds.
- Then `loopAfter()` updates the follower, and the follower calls your drivetrain's `drive`. The
  wheels' powers go to the motors.

### STOP

:::{admonition} fig-e111-stop
:class: pencil
Stand-in for `fig-e111-stop`, made by `book/tools/draw.py`.
:::

`stopAfter()` tells the follower to stop, and then the drivetrain sends zero to each motor.
