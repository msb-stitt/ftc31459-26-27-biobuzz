# 154 what's happening: the scheduler runs your runs

When the computer runs your program, it reads one line of code at a time. It moves words and
numbers around in its memory. It is like moving sticky notes around on your desk.

In [L153](l153.md) you typed `theRuns()`. Calling it drives nothing. It makes **commands**, and the
scheduler runs them later, a little each loop. This page draws how, with the UML marks from
[E067](e067.md), [L093](l093.md) and [E111](e111.md).

## a command

:::{admonition} fig-e154-classes
:class: pencil
Stand-in for `fig-e154-classes`, made by `book/tools/draw.py`.
:::

`Command` is an interface from Pedro Pathing. A command is an object the scheduler works on. The
scheduler calls three of its methods:

- `start()`, once, when the command begins.
- `execute()`, once each loop.
- `done()`, after each `execute()`. It gives back `true` when the command is finished.

`instant`, `waitUntil` and `Commands.infinite` each make a `CommandBuilder`, which is-a `Command`.
Each one fills in one part:

- `instant(this::stopTheRun)` calls `stopTheRun()` in its `start()`. Its `done()` is always
  `true`.
- `waitUntil(this::timeToStop)` does nothing. Its `done()` calls `timeToStop()` and gives back what
  it says.
- `Commands.infinite(this::measure)` calls `measure()` in each `execute()`. Its `done()` is never
  `true`.

`this::measure` hands over the method itself, to be called later. It does not call it now.

`sequential` makes a `Sequential`, which is-a `CommandBuilder`. It holds (has-a) a list of commands
in its field `commands`, and works on one at a time. A `Sequential` is a "kind of" `Command` too, so
a sequential can hold sequentials. Your `runs` holds `turnRuns`, `forwardRuns` and `strafeRuns`.
Each of those holds a `run` for each power, and each `run` holds its steps:

```{code-block} java
:caption: mytry/L153FeedforwardOpMode.java

    Command oneRun(Axis runAxis, double runPower) {
        Command run = sequential(
                instant(() -> startTheRun(runAxis, runPower)),
                waitUntil(this::timeToStop),
                instant(this::stopTheRun),
                waitUntil(this::standingStill),
                instant(this::finishTheRun));
        return run;
    }
```

The scheduler holds (has-a) each command it is running in its field `runningCommands`.

## PLAY

:::{admonition} fig-e154-start
:class: pencil
Stand-in for `fig-e154-start`, made by `book/tools/draw.py`.
:::

```{code-block} java
:caption: mytry/L153FeedforwardOpMode.java

    public void start() {
        startBefore();
        Command measureEveryLoop = Commands.infinite(this::measure);
        Scheduler.schedule(measureEveryLoop);
        Command runs = theRuns();
        Scheduler.schedule(runs);
        startAfter();
    }
```

- `start()` hands `measureEveryLoop` to the scheduler. Then `theRuns()` makes `runs`. The robot
  does not move yet.
- `schedule(runs)` calls `runs.start()` at once. That starts `turnRuns`, which starts its first
  `run`, which starts its first step. That step is an `instant`, so `startTheRun(TURN, 0.2)` runs
  before the first loop.

## each loop

:::{admonition} fig-e154-loop
:class: pencil
Stand-in for `fig-e154-loop`, made by `book/tools/draw.py`.
:::

Each `loop()` ends with `loopAfter()`, which calls the scheduler's `execute()`. The scheduler goes
through its commands in the order they were scheduled:

- First `measureEveryLoop`. Its `execute()` calls your `measure()`. Its `done()` says `false`, so
  it stays.
- Then `runs`. Its `execute()` is handed down to the step under way. Here that step is the wait, so
  `run` asks your `timeToStop()`. It says `false`, and nothing else happens this loop.

So `measure()` runs every loop, beside the run. `timeToStop()` is asked once a loop, until it says
`true`.

## when a wait is over

:::{admonition} fig-e154-wait-ends
:class: pencil
Stand-in for `fig-e154-wait-ends`, made by `book/tools/draw.py`.
:::

On the loop `timeToStop()` says `true`, the wait is over. `run` moves to its next step and starts
it in the same loop. That step is `instant(this::stopTheRun)`, so `stopTheRun()` runs right away.

An `instant` is done as soon as it starts. `run` sees that on the next loop, and starts the step
after it then.

When `run`'s last step is done, `run` is done, and `turnRuns` starts its next `run`. When
`turnRuns` is done, `runs` starts `forwardRuns`. When `runs` is done, the scheduler drops it.
`measureEveryLoop` is never done, so it runs until STOP.

The PLAY and loop diagrams leave out a step: `runs` hands each call to `turnRuns`, and `turnRuns`
hands it on to `run`. The note "through turnRuns" marks it.
